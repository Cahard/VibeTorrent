### 0.2. Исходные данные и допущения (проверено 2026-10-27)

1. `README.md` **в корне репозитория отсутствует**. Прочитан `docs/agents/README.md` (роли, стек, общие правила: тёмная тема, ru-RU, без телеметрии, обновления UI ≤ 2 Гц, виртуализация списков, min touch target 32 px, контраст AA).
2. Каталога `src/` и файлов решения (`.sln`, `.csproj` продукта) в рабочей копии **нет**. План описывает целевое поведение и контракты; после появления кода добавляется обратная трассировка «класс → TC».
3. Локальный SDK: `D:\VibeTorrent\.dotnet\dotnet.exe`, версия **10.0.403**. Все команды в документе используют этот путь (глобальный SDK может отсутствовать).
4. Пакеты MonoTorrent **3.0.2** и зависимости (`Mono.Nat 3.0.0`, `ReusableTasks 4.0.0`) лежат в `artifacts/packages`; сборки внутри пакета имеют версию сборки `2.0.0.0` — это ожидаемо и не является дефектом (учитывать при разборе логов/дампов).
5. Ключевые API-факты, на которые опираются кейсы (проверены по сборке, не по памяти):
   - `ClientEngine.AddAsync(...)`, `RemoveAsync(TorrentManager, RemoveMode)`, `SaveStateAsync()`, `RestoreStateAsync(...)`, `StopAllAsync(TimeSpan)`, `DownloadMetadataAsync(MagnetLink, CancellationToken)`.
   - `RemoveMode` имеет значения **`KeepAllData`, `CacheDataOnly`, `DownloadedDataOnly`, `CacheDataAndDownloadedData`** — отдельного «удалить всё» нет. «Удалить с данными» обязано маппиться на `CacheDataAndDownloadedData` (см. Q-2), иначе кнопка «с данными» молча оставит файлы.
   - `TorrentManager`: `PauseAsync`, `StartAsync`, `StopAsync(TimeSpan)`, `HashCheckAsync(bool)`, `SetFilePriorityAsync(ITorrentManagerFile, Priority)`, `MoveFilesAsync(string, bool)`, `SaveFastResumeAsync()`, `LoadFastResumeAsync(FastResume)`, `WaitForMetadataAsync(CancellationToken)`, `TrackerManager`, `Peers`, `Files`, `Monitor`, `Error`, `State`.
   - `TorrentState`: `Stopped, Paused, Starting, Downloading, Seeding, Hashing, HashingPaused, Stopping, Error, Metadata, FetchingHashes` — состояния `HashingPaused`, `Metadata`, `FetchingHashes` обязаны иметь отдельные визуальные статусы (см. TC-027, TC-013).
   - `Priority`: `DoNotDownload, Lowest, Low, Normal, High, Highest, Immediate`.
   - `TorrentSettings`: `AllowDht`, `AllowPeerExchange`, `AllowInitialSeeding`, `MaximumConnections`, `MaximumDownloadRate`, `MaximumUploadRate`, `CreateContainingDirectory` — лимиты живут и на уровне торрента, и на уровне движка (`EngineSettings.MaximumDownloadRate/UploadRate`), поэтому «глобальный лимит» — это вычисляемая величина, а не одно свойство.
   - `EngineSettings`: `AllowedEncryption`, `AllowPortForwarding`, `AllowLocalPeerDiscovery`, `FastResumeCacheDirectory`, `FastResumeMode`, `AutoSaveLoadFastResume`, `ListenEndPoints`, `CacheDirectory`, `DiskCacheBytes`.
   - `Torrent.Load(ReadOnlySpan<byte>)` / `Torrent.Load(BEncodedDictionary)` бросают исключения на мусоре → обязателен перехват и пользовательская ошибка (TC-015…TC-017).
   - `MagnetLink.FromUri(Uri)` — единственная точка разбора magnet; вызывать только после собственной валидации схемы/размера (TC-010, TC-011, TC-070).

### 0.3. Не в области тестирования v1.0

- macOS/Linux, Windows 10 и ниже (если не будет заявлено отдельно), ARM64.
- Веб-сид за пределами «не ломает загрузку» (глубокое тестирование BEP-19 не требуется).
- Собственный трекер, VPN-интеграция, RSS, планировщик, мобильные клиенты.
- Совместимость с форматами `.torrent`, созданными экзотическими клиентами старше 2010 г., кроме случаев в FX-13.

## 1. Стратегия тестирования

### 1.1. Цели и принципы

1. **Данные важнее функций**: любой сценарий, способный испортить/удалить пользовательские файлы или состояние сессии, имеет приоритет P1 независимо от «редкости».
2. **Риск-ориентированность**: 60% усилий — на добавление/валидацию, файловую безопасность, персистентность и восстановление; 20% — на UI/доступность; 20% — на сеть/лимиты/перф.
3. **Воспроизводимость без интернета**: по умолчанию все функциональные проверки идут на loopback или на фикстурах, без внешней сети. Внешняя сеть — только в отдельном smoke-прогоне (ENV-7) и никогда не является единственным доказательством.
4. **Наблюдаемость**: каждый дефект обязан прикладывать evidence (лог, дамп, ETW-трейс, скриншот, `state.json` до/после). «Не воспроизводится» без evidence не принимается.
5. **Сдвиг влево**: path safety, атомарность состояния, форматтеры и ViewModel-логика покрываются unit-тестами до появления GUI.
6. **Никакой телеметрии в тестах**: тестовые прогоны не отправляют данные наружу; сетевой захват — часть приёмки (TC-064).

### 1.2. Уровни тестирования

| Уровень | Что проверяем | Инструменты | Доля | Где запускается | Критерий прохождения |
|---|---|---|---|---|---|

| Integration (in-proc) | Реальный `ClientEngine` + `TorrentManager` на loopback, локальный HTTP-трекер (`TrackerServer`/`HttpTrackerListener`), fast resume, `RemoveMode`, `MoveFilesAsync`, поведение при отмене/таймаутах | xUnit + `Trait("Category","Swarm")`, temp-профиль, реальные файлы | ~20% | Nightly + релизный прогон | 0 failed; допускается 1 ретрай на кейс, стабильность ≥ 95% за 10 прогонов |

### 1.3. Автоматизируем / не автоматизируем

**Автоматизируем обязательно:** path safety, bencode/magnet-валидация, форматтеры, ETA, сериализация+атомарность, fast resume load/save (in-proc), `RemoveMode`, clamp лимитов, фильтры/сортировка/поиск, команды и `CanExecute`, восстановление из повреждённого состояния, редакция логов, контракт «нет сети» (network guard).

**Не автоматизируем (ручное/полуручное):** screen reader (NVDA/Narrator), реальные DPI-режимы и mixed-DPI, спящий режим/гибернация, физическое отключение диска, диск full через VHD, антивирусные конфликты, субъективное качество тёмной темы и анимаций, поведение трея на панели задач с переполнением, single-instance через Explorer.

### 1.6. Процесс, регресс, flaky-политика

1. Полный регресс — перед релизом; smoke (TC-001, 003, 007, 013, 022, 027, 030, 031, 044, 054, 057) — на каждый билд.
2. Дефект принимается только с: воспроизводимостью (всегда/частота), evidence, ID требования и указанием окружения.
3. Flaky-тест не «лечится» ретраями молча: он получает метку `quarantine`, тикет на стабилизацию ≤ 5 рабочих дней, иначе удаляется из гейта.
4. Каждый фикс дефекта S1/S2 обязан сопровождаться регрессионным тестом (unit или integration). Без теста фикс не считается закрытым.
5. Трассируемость: требование → тест-кейсы → автотест → дефект. Матрица раздела 2 — источник истины; тест без требования помечается `orphan` и удаляется или привязывается.
6. Прогон фиксируется отчётом: сборка, дата, окружения, результаты по кейсам, список дефектов, отклонения от бюджета, вердикт.

## 3. Тест-кейсы

Формат: ID · приоритет · название. Далее — требование, данные, предусловия, шаги, ожидаемый результат, негативные границы. Если ожидание зависит от продуктового решения, указан открытый вопрос `Q-N` (раздел 8.3).

### Группа A. Запуск, single-instance, интеграция с ОС

#### TC-001 · P1 · Свежий запуск на чистом профиле
- **Требование:** R-01. **Уровень:** UI smoke + manual. **Данные:** нет.
- **Предусловия:** профиль удалён (`%LOCALAPPDATA%\VibeTorrent` отсутствует); Release-билд; сеть отключена; пользователь без прав администратора.
- **Шаги:**
  1. Запустить `VibeTorrent.exe`.
  2. Замерить время до появления интерактивного окна (секундомер/ETW).
  3. Проверить дерево `%LOCALAPPDATA%\VibeTorrent` (файлы, подкаталоги, права).
  4. Осмотреть список, строку состояния, счётчики скоростей.
  5. Закрыть приложение, запустить повторно.
- **Ожидаемо:** окно появляется: холодный старт ≤ 3,0 с, тёплый ≤ 1,0 с (PERF-07); создаются только документированные подкаталоги (`cache\`, `logs\`, `torrents\`), права — только текущий пользователь; пустое состояние: заголовок «Пока нет торрентов», кнопка «Добавить торрент», подсказка про drag&drop и `Ctrl+O`; список пуст, счётчики `0 Б/с`; ни одного сетевого соединения (DHT off) либо только bootstrap DHT (DHT on); окно не требует admin; в реестре нет записей, кроме документированного ключа автозапуска (и только если пользователь его включил); повторный запуск открывает то же состояние без дублей.
- **Негатив:** если `%LOCALAPPDATA%` переполнен/недоступен — см. TC-002.

#### TC-002 · P2 · Первый запуск при недоступном профиле
- **Требование:** R-01, R-43. **Уровень:** manual. **Данные:** ACL deny на `%LOCALAPPDATA%\VibeTorrent`.
- **Предусловия:** каталог создан; `icacls "%LOCALAPPDATA%\VibeTorrent" /deny "%USERNAME%:(OI)(CI)(W)"`.
- **Шаги:** 1) запустить приложение; 2) прочитать диалог; 3) проверить, не создано ли частичное состояние; 4) снять deny, запустить снова.
- **Ожидаемо:** один понятный диалог с полным путём и причиной («нет прав на запись»), без стека и без «Unhandled exception»; приложение не оставляет полупустой профиль и не работает «в памяти» с последующей потерей данных; предлагается выбрать другую папку данных или выйти; после восстановления прав запуск успешен, состояние не повреждено.
- **Негатив:** запрещено молча писать в `%TEMP%` и потом «терять» сессию.

#### TC-003 · P1 · Второй экземпляр при запущенном приложении
- **Требование:** R-02. **Уровень:** UI smoke. **Данные:** FX-01.
- **Предусловия:** приложение запущено, в списке ≥ 1 торрент; окно развёрнуто; второй запуск из Explorer/консоли.
- **Шаги:** 1) запустить `VibeTorrent.exe` второй раз; 2) замерить время выхода второго процесса; 3) проверить окно первого; 4) повторить, когда первое окно свёрнуто в трей; 5) проверить `state.json` (mtime, отсутствие `.tmp`).
- **Ожидаемо:** второй процесс завершается ≤ 1,5 с с кодом 0; активируется существующее окно (из трея — восстанавливается и выходит на передний план); не создаётся второе окно, второй `ClientEngine`, второй слушающий порт; `state.json` не переписывается вторым процессом; в логе одна запись «forwarded to existing instance».
- **Негатив:** гонка при одновременном старте двух процессов (запустить оба в течение 100 мс, 20 итераций) — всегда один экземпляр, без повреждения состояния.

#### TC-004 · P1 · Второй экземпляр с аргументами
- **Требование:** R-02, R-07. **Уровень:** UI smoke. **Данные:** FX-01, FX-14 (валидный magnet).
- **Предусловия:** первый экземпляр запущен.
- **Шаги:** 1) выполнить `VibeTorrent.exe "D:\fx\single-1mb.torrent" "magnet:?xt=urn:btih:<hash>&dn=Test" --minimized`; 2) проверить список и уведомление; 3) повторить с несуществующим путём впереди валидного; 4) повторить с уже добавленным торрентом.
- **Ожидаемо:** оба элемента добавлены в существующий экземпляр; при `--minimized` окно не активируется, показывается toast; невалидный путь даёт ошибку только по нему, валидный добавляется; дубликат не добавляется второй раз (фокус на существующем); порядок аргументов сохранён; кавычки/пробелы/кириллица обрабатываются корректно.

#### TC-005 · P2 · Ассоциация `.torrent` (двойной клик в Explorer)
- **Требование:** R-03. **Уровень:** manual. **Данные:** FX-01.
- **Предусловия:** ассоциация включена установщиком или пользователем; приложение не запущено.
- **Шаги:** 1) двойной клик по `single-1mb.torrent`; 2) повторить при запущенном приложении; 3) проверить диалог добавления, отменить; 4) проверить, что ассоциация не перехватывает `.torrent` у другого клиента без согласия.
- **Ожидаемо:** приложение стартует/активируется, диалог добавления предзаполнен (имя, размер, папка по умолчанию); при отмене ничего не добавлено; при повторном клике — без второго процесса; установщик не назначает ассоциацию принудительно (Windows 11 требует выбор пользователя).

#### TC-006 · P2 · Обработчик `magnet:` из браузера
- **Требование:** R-03. **Уровень:** manual. **Данные:** FX-14.
- **Шаги:** 1) клик по magnet-ссылке в браузере; 2) проверить диалог (имя из `dn`, отсутствие размера); 3) отменить; 4) открыть `magnet:` без параметров и `magnet:?xt=urn:btih:ZZZ`.
- **Ожидаемо:** диалог с корректным именем; отмена — без следов; невалидные ссылки дают сообщение «Некорректная magnet-ссылка» и не роняют приложение; параметр `tr` попадает в список трекеров, `xl` — в ожидаемый размер; полный magnet не пишется в лог (TC-065).

### Группа B. Добавление торрентов

#### TC-007 · P1 · Добавление валидного `.torrent` через кнопку
- **Требование:** R-04. **Уровень:** UI smoke. **Данные:** FX-01.
- **Предусловия:** ENV-1, чистый профиль, папка `D:\vt\dl` существует и пуста.

- **Ожидаемо:** диалог открывается ≤ 300 мс; метаданные отображаются полностью (имя, 1 МиБ, 1 файл, трекер); после добавления строка появляется ≤ 500 мс, состояние `Загрузка` (или `Ожидание метаданных` для magnet); прогресс и ETA обновляются не чаще 2 раз/с; файл создаётся в `D:\vt\dl\<name>`; в логе — infohash, а не полный путь к `.torrent`; кнопка «Добавить» недоступна повторно во время операции (нет двойного добавления).

#### TC-008 · P2 · Drag&drop трёх файлов, один битый

#### TC-009 · P2 · Drag&drop папки и не-торрент файла

#### TC-012 · P2 · Командная строка

#### TC-013 · P1 · Magnet без метаданных

#### TC-019 · P2 · Дубликат magnet ↔ `.torrent`, гибрид v1+v2

### 4.4. Ключевые техники

#### 4.4.1. Атомарный JSON — контракт и проверки

Контракт `IAtomicFileStore.WriteAsync<T>(path, value)`:

1. сериализовать в `path.tmp-<guid>` в **той же** директории (атомарность `Move` требует одну ФС);
2. `FileStream` с `FileOptions.WriteThrough`, затем `Flush(flushToDisk: true)`;
3. `File.Replace(tmp, path, path.bak)` (первая запись — `File.Move(tmp, path)`);
4. при любой ошибке — удалить `tmp`, исходный файл не трогать;
5. чтение: `path` → при ошибке `path.bak` → при ошибке пустое состояние + `state.corrupt-<utc>.json`, **никогда** не читать `*.tmp`.

Обязательные тесты:

- `Write_LeavesNoTempFiles_AndBakIsPreviousVersion` — после 3 записей в каталоге ровно `state.json` + `state.json.bak`.
- `Read_UnderConcurrentWrites_NeverSeesPartialJson` — 1 писатель (500 циклов) + 3 читателя; каждый результат либо парсится, либо `Empty`; ни одного `JsonException` наружу.
- `Write_WhenReplaceFails_OldStateStillValid` — `FaultyFileStore` бросает `IOException` перед replace; старый файл парсится, tmp отсутствует.
- `Write_DiskFull_DoesNotCorruptState` — `IOException` c HRESULT `0x70`/`0x27`; состояние прежнее.
- `Read_Corrupt_WithValidBak_RestoresAndLogs`.
- `Read_BothCorrupt_PreservesFile_AndReturnsEmpty` — файл `state.corrupt-*` создан, исходный не удалён.
- `Read_FutureSchema_ThrowsTypedError_AndDoesNotOverwrite` — попытка сохранить поверх не происходит.
- `Save_NoChanges_DoesNotTouchFile` — mtime не меняется (защита от износа SSD и лишних записей).
- `Bak_IsReadable_ByPreviousVersion` — golden-совместимость.

#### 4.4.2. Path safety — property-based

```csharp
[Property(MaxTest = 2000)]
public Property Sanitized_Path_Always_Stays_Inside_Root(NonEmptyString raw)
    => Prop.ForAll(...).QuickCheckThrowOnFailure();
```

Инварианты (FsCheck, 2 000 кейсов на свойство):

1. `Canonical(Sanitize(name), root)` начинается с `root + separator` (OrdinalIgnoreCase) — для любых входов.
2. `Sanitize(Sanitize(x)) == Sanitize(x)` (идемпотентность).
3. `Sanitize(x) != ""` и не содержит `..` как сегмент, `:`, `\0`, `/`, `\` внутри сегмента.
4. Зарезервированные имена (`CON`, `NUL`, `PRN`, `AUX`, `COM1..9`, `LPT1..9`) не остаются зарезервированными.
5. Компонент ≤ 255 байт UTF-8 после санитизации.
6. Для набора «злых» имён (`..\..\x`, `\\srv\s`, `C:\x`, `a:b`, `x.`, `x `, `x\u0000y`, RTL-строка) — результат соответствует документированной таблице маппинга (golden-файл, 50 строк).
7. `Resolve` не выполняет сетевой доступ: `FakeFileSystemInfo` фиксирует 0 обращений к UNC.

Отдельный тест-предохранитель: `Resolve_WhenCalledWithUncPath_ThrowsPathNotAllowed` — запрещает даже попытку.

#### 4.4.3. Форматтеры и ETA

- Табличный `[Theory]` с `MemberData`, культура `ru-RU` (и `Invariant` — для логов): `0`, `1`, `1023`, `1024`, `1536`, `1_048_576`, `long.MaxValue`, `-1`, `double.NaN`, `double.PositiveInfinity`.
- Правила: `-1`/`NaN` → «—» и warning в лог, а не `-1 Б`; `∞` только в ETA при нулевой скорости; округление `AwayFromZero`; единицы — одна система на всё приложение (тест-константа).
- ETA: формула `Eta = remainingBytes / emaRate`, `emaRate` — EMA с α = 0.2 по `TimeProvider.GetTimestamp()` (не `DateTime.Now`); при `remaining == 0` → «Готово»; при `rate == 0` → «—»; при скачке часов назад значение не становится отрицательным; при `remaining > 1e18` нет overflow (использовать `double` с проверкой).
- Тест «монотонность»: 100 последовательных обновлений с шумом ±30% → ETA не скачет более чем в 2 раза между соседними тиками (иначе UI «дёргается»).

#### 4.4.4. Сериализация состояния

- Round-trip property: `Deserialize(Serialize(x))` эквивалентен `x` по значимым полям (сравнение через `record`/`IEquatable`, не рефлексией).
- Golden-файлы (`Verify`/snapshot) для схемы: любое изменение сериализованного вида — осознанный diff в PR.
- Enum'ы — строками (`"Paused"`, а не `3`), иначе перестановка значений ломает совместимость.
- Неизвестные поля игнорируются без исключения; отсутствующие — дефолты; несовпадение типов — поле пропускается с записью в лог, остальное читается.
- `schemaVersion` — монотонно; при `version > current` запись запрещена (read-only), пользователю — сообщение.

#### 4.4.5. ViewModel-логика

- ViewModel не знает про `Dispatcher`: `IUiDispatcher` c `ImmediateDispatcher` в тестах; тест-скан (архитектурный) запрещает `System.Windows.Threading` в `VibeTorrent.App.ViewModels` (кроме явно разрешённых файлов).
- `FakeTorrentEngine` реализует `ITorrentEngine` с управляемыми состояниями, счётчиками вызовов и «зависающими» задачами (`TaskCompletionSource` без `SetResult`) для проверки `IsBusy`/отмены.
- Батчинг: `NotificationBudgetTests` подписывается на `PropertyChanged`, прогоняет 60 «тиков» движка и требует ≤ 2 обновлений/с на торрент и ≤ 2 000 суммарно; отсутствие `CollectionChanged` с `Reset`.
- Утечки подписок: подписать VM на фейковый движок, вызвать `Dispose`, `GC.Collect`, проверить `WeakReference.IsAlive == false`.
- Команды: для каждой — `CanExecute` в состояниях «нет выделения», «идёт операция», «нет прав»; проверка, что двойной клик не запускает две операции (счётчик вызовов = 1).

#### 4.4.6. Локальный сидер/личер — реалистично ли

**Вердикт: да, реалистично в одном процессе, с тремя оговорками.**

Схема `SwarmFixture`:

1. `TrackerServer` + `HttpTrackerListener` на `127.0.0.1:0` (типы есть в `MonoTorrent.Trackers`), announce URL `http://127.0.0.1:<port>/announce`; торрент генерируется `TorrentCreator` с этим URL.
2. Два `ClientEngine`: сидер (`SavePath` с готовыми данными) и личер (`SavePath` пустой), разные `PeerId`, `AllowPortForwarding=false`, `AllowLocalPeerDiscovery=false`, DHT off, `FastResumeMode=None` для чистоты.
3. `TorrentManager` у сидера — `StartAsync` + `HashCheckAsync`, у личера — `StartAsync`.
4. Таймаут 60 с, опрос `Progress` каждые 200 мс, ассерт «100% и SHA1 совпадает».

Оговорки:
- **loopback-пиры.** MonoTorrent может считать 127.0.0.1 «локальным» пиром; если соединение не устанавливается — обходить трекер и добавлять пира напрямую: `leecher.AddPeerAsync(new PeerInfo(new Uri("tcp://127.0.0.1:<port>")))`. Это документированный fallback, а не хак.
- **порты.** `ListenEndPoints` требует явный endpoint; свободный порт берётся через `TcpListener(IPAddress.Loopback, 0)` + немедленное освобождение → возможна гонка, поэтому 3 попытки с новым портом.
- **стабильность.** Ожидаемая флакиность 1–3% (тайминги, антивирус, медленный CI). Политика: `Trait("Category","Swarm")`, nightly, максимум 1 ретрай; при стабильности < 95% за 10 прогонов — тест переводится в manual с локальным сидером (qBittorrent, без интернета), а не «чинится» ретраями.

Если loopback-сварм окажется нестабильным в конкретной среде, **не** заменять его моками MonoTorrent: критичные для данных сценарии (удаление с данными, перемещение, fast resume) обязаны проверяться на реальном движке — иначе тесты будут подтверждать фейк.

### 4.6. Что осознанно не покрываем unit-тестами

Диск full на реальной ФС, DPI, screen reader, сон, смена сети, антивирус, поведение `NotifyIcon` при рестарте Explorer, установщик. Это ручные кейсы (TC-050, TC-056…TC-060, TC-063, TC-071). Мокать их в unit-тестах — создавать ложную уверенность.

## 5. Performance-бюджеты

### 5.1. Методика

- Сборка: `Release`, `PublishReadyToRun=true`, x64, без отладчика. ENV-1 (для RAM/старта — ENV-3).
- Фикстуры: FX-17 (150 торрентов; для бюджета «100» считается подмножество 100), FX-03 (10k файлов), FX-04 (4 GiB).

### 5.3. Особые проверки

- **Отсутствие утечек событий:** после 200 циклов «открыть/закрыть панель деталей» и 100 «добавить/удалить торрент» число подписчиков движка не растёт (инструментированный счётчик), WS возвращается к базе ±10%.
- **Отсутствие busy-loop:** при потере сети и недоступном трекере CPU ≤ 3% (TC-048, TC-049); проверять 5 минут.
- **Стабильность FPS при 200% DPI:** анимации на transform/opacity, без `Effect`/`Blur` в анимируемых элементах (проверка WPA: нет software rendering, `RenderCapability.Tier >= 2`).
- **Деградация под антивирусом:** повторить PERF-03/PERF-07 на ENV-1 с включённым Defender real-time; допустимая деградация старта ≤ 50%, иначе — оптимизация I/O.

### 6.1. Шаблон баг-репорта

```markdown

| Метки | SEC / DATA / PRIV / PERF / A11Y / I18N / REGRESSION |
| Компонент | Add / Session / Remove / PathSafety / UI-List / Details / Limits / Tray / Settings / Installer |

| Окружение | ENV-N, Win11 24H2, 125%, профиль с кириллицей |
| Воспроизводимость | Всегда / 8 из 10 / Один раз |
| Дата / автор | 2026-10-27 / QA |

**Предусловия:** …
**Шаги:**
1. …
2. …
**Ожидаемый результат:** …
**Фактический результат:** …
**Evidence:**
- лог: `%LOCALAPPDATA%\VibeTorrent\logs\app-20261027.log` (фрагмент, строки 120–140);
- `state.json` до/после (вложение, секреты вырезаны);

- для сетевых: фрагмент захвата (без passkey).
```

Правила: заголовок без «не работает» (что именно и где); один дефект = одна проблема; секреты и полные magnet в тикете запрещены; для S1/S2 обязателен дамп/трейс; «плавающий» дефект требует частоты и условий.

### 6.2. Severity

| Severity | Определение | Примеры для VibeTorrent |
|---|---|---|
| **S1 Blocker** | Потеря/порча пользовательских данных, нарушение безопасности, невозможность пользоваться продуктом, утечка приватности | запись файла вне папки загрузки (path traversal/UNC); удаление с данными удаляет чужие файлы; повреждение `state.json` при штатном закрытии; падение при старте/добавлении; приватный торрент анонсируется в DHT; passkey в открытом виде в логе; любой сетевой трафик с телеметрией; удаление без данных фактически удаляет файлы |
| **S2 Critical** | Основная функция не работает, обхода нет или он неприемлем; зависание/краш в поддерживаемом сценарии | загрузка не начинается на валидном торренте; «удалить с данными» оставляет файлы (не тот `RemoveMode`); лимиты игнорируются; прогресс теряется при штатном перезапуске; UI зависает > 5 с на 10k файлов; второй экземпляр пишет в то же состояние; при 100 торрентах падение/ANR; DPI 200% делает интерфейс нечитаемым |
| **S3 Major** | Функция работает с заметным дефектом, есть обход | сортировка/фильтр сбрасываются; график показывает неверные значения; трекер не переannounce после сети; ложные ошибки на валидных торрентах; drag&drop теряет часть файлов; ETA абсурден; панель пиров не обновляется |
| **S4 Minor** | Косметика, локализация, неудобство без потери функций | обрезанный текст при 125%; нет склонения «5 торрент»; неверный фокус-порядок в диалоге; тултип не появляется; иконка трея не восстанавливается после Explorer restart (если обходится перезапуском) |
| **S5 Trivial** | Мелочь, не влияющая на работу | опечатка, дрожание анимации, выравнивание на 1 px |

**Полы severity (нельзя понизить):** path traversal/запись вне корня → S1; удаление/перемещение с потерей данных → S1; приватность (DHT для private, passkey, телеметрия) → S1; невозможность восстановить сессию → S2 минимум; зависание UI > 5 с → S2; падение любого рода → S2 минимум, при потере данных → S1.

### 6.3. Priority и SLA

| Priority | Значение | SLA фикса |
|---|---|---|
| P1 | Блокирует релиз/основной сценарий | S1 — 1 рабочий день, S2 — 3 |
| P2 | Должно быть исправлено в релизе | S2 — 5, S3 — 10 |
| P3 | Следующий релиз | S3/S4 — без жёсткого SLA, в бэклог |

## 8. Приложения

### 8.1. Генерация фикстур

Инструмент `tools/FixtureGen` (тестовый, в поставку не входит) на MonoTorrent: `TorrentCreator`/`EditableTorrent` + `ITorrentFileSource`. Контракт:

```
FixtureGen --out D:\vt\fx --case single-1mb
FixtureGen --out D:\vt\fx --case multi-200 --files 200 --size 256KiB
FixtureGen --out D:\vt\fx --case files-10k --files 10000 --size 1KiB
FixtureGen --out D:\vt\fx --case traversal --names-file traversal.txt
FixtureGen --out D:\vt\fx --case magnet --info-hash <hex> --dn "Тест"
```

Требования к генератору: детерминированный вывод (фиксированные `creation date`, `piece length`, порядок файлов); запись `fx/manifest.json` с SHA256 каждого файла; поддержка «злых» имён через `--names-file` (по строке на файл, UTF-8, включая `..\`, UNC, NUL-эскейпы). Тяжёлые данные (4 GiB) создаются sparse: `fsutil file createnew D:\vt\fx\big.bin 4294967296` + запись первых/последних блоков, чтобы хеш был детерминирован (или генерация реальных данных — по решению команды, но с фиксированным seed).

Дисковые условия (ручные, требуют прав):
```powershell
# диск full: VHD 200 МБ
New-VHD -Path D:\vt\small.vhdx -SizeBytes 200MB -Fixed
Mount-VHD -Path D:\vt\small.vhdx
Initialize-Disk -Number <n> -PartitionStyle MBR
New-Partition -DiskNumber <n> -UseMaximumSize -DriveLetter V
Format-Volume -DriveLetter V -FileSystem NTFS -NewFileSystemLabel VTSMALL

# read-only папка
icacls D:\vt\ro /deny "$env:USERNAME:(OI)(CI)(W)"

# длинные пути (требует admin)
Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem' LongPathsEnabled 1
```

### 8.2. Глоссарий

| Термин | Значение |
|---|---|
| infohash | SHA1 (v1) / SHA256 (v2) идентификатор содержимого торрента |
| fast resume | сохранённый битфилд + нехэшированные куски, ускоряющий старт |
| HashingPaused | состояние MonoTorrent: проверка файлов приостановлена |
| `RemoveMode` | режим удаления в MonoTorrent; «с данными» = `CacheDataAndDownloadedData` |

| WS | working set, рабочий набор процесса |
| soak | длительный прогон (8–24 ч) для поиска утечек и деградации |
| flaky | нестабильный тест, результат которого зависит от окружения/таймингов |
